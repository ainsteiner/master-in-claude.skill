# 译本更新规范（原书风格 · 2026-11 版）

本文件是给执行更新的写作者用的唯一规范。所有章节更新必须遵守；与本文冲突的任何历史说明一律以本文为准。

---

## 1. 目标

把中文全译本 `zh/NN_*.md` **原地更新到 2026-11 现状**，读起来仍像 Stephen Clear 写的一本书，而不是"原书 + 补丁"。

- 不新增独立补丁册，不写"更新说明""编者按""2026-11 新增"这类字样进正文。
- 结构、章节号、标题体系、四类提示框、本章要点一律保留。
- 只改内容，不改书的骨架。

---

## 2. 原书风格（必须复现）

### 2.1 口吻

- **第一人称操作者**：可用「我给客户讲的心智模型是……」「我带过的一个团队……」「我见过最烧钱的错误……」。
- **短句为主，允许长句但必须有节奏**；忌学术腔、忌营销腔、忌机翻腔。
- **比喻要具体、可落地**：「雇个外科医生来贴创可贴」「资深合伙人 / 骨干 / 初级员工」「一家公司要是每场会都派资深合伙人去，迟早破产」。
- **诚实边界**：给数字的同时说明它会变，例如「确切上限会随模型与档位变，去官方文档核对当前数字」。
- **不吹**：不用「革命性」「颠覆」「史诗级」；对厂商自述数字要标「厂商自述」。

### 2.2 章节骨架（顺序固定）

```
第 N 章

# 章节标题（与原文一致，除非该章主题已变）

✦

开篇钩子：3 段左右，从一个具体痛点或反常识判断切入，不用"本章将介绍"

## 小节标题
（正文段落）

> **避坑提醒** 单段，具体场景 + 代价 + 怎么避开

## 小节标题
...

## 本章要点
- 5–8 条，每条一句话，可独立成立
```

### 2.3 四类提示框（正文引用块，单段）

| 标签 | 用途 | 写法 |
|---|---|---|
| `> **操作者锦囊**` | 提高上限的技巧、组合打法 | 给一个可立即用的做法 + 为什么划算 |
| `> **动手任务**` | 让读者动手 10–30 分钟 | 具体动作 + 完成判据 |
| `> **避坑提醒**` | 常见错误与代价 | 具体场景 + 损失 + 正确做法 |
| `> **一线经验**` | 实战观察、失败复盘 | 第一人称案例 + 结论 |

- 每章正文（非前置/附录）宜各出现 0–2 次，不要每节都塞。
- 原章已有的框**保留位置**，内容可改写；不要为了"看起来更新过"而新增框。

### 2.4 禁止的写法

- 禁止出现：`本版更新`、`2026-11 更新`、`原书此处已过时`、`编者注`、`译者按`、`（新增）`。
- 禁止把事实写成流水账（"Fable 5.2 于 11 月 9 日发布，价格 8/40，上下文 1M……"），必须嵌进判断里。
- 禁止删除原有的 `## 本章要点`。
- 禁止把标题里的产品名换成"某产品"之类的模糊说法。

## 3. 三类更新动作

### 3.1 事实替换（不改论证结构）

把型号、价格、窗口、参数、界面名、日期换掉，**论证与比喻保留**。

示例（09 章）：
- 原：「Claude Opus 4.8 是旗舰……Claude Sonnet 4.6 是均衡的干活主力……Claude Haiku 4.5」
- 新：「Claude Opus 5.5 是日常主力……Claude Fable 5.2 是凌驾于 Opus 之上的顶配……Claude Sonnet 5.5 / Haiku 5.5」
- **注意**：型号换了，档位关系也变了 —— 原书是"三档"，现在是"三档 + 一个更高的 Fable 层"。比喻要顺势扩写，不能只换数字。

### 3.2 方法论重写（必须真改，不能只换名词）

以下三处是**判断反转**，整段重写：

**A. 默认模型**：原书「Sonnet 是默认，证据推着往上抬」→ 现在「官方建议从 Opus 5.5 + medium effort 起步，因为更强模型用更少 token 完成，总成本更低；效果不达预期先调 effort 再换模型」。
写法要求：**保留原书的"证据推着走"精神，但把起点改了**，并解释为什么（省的是总工作量，不是单价）。

**B. 常驻上下文**：原书「系统提示词一次把重活干了」「五配料」「约束写清」→ 现在「常驻上下文要减规则，让模型用判断；CLAUDE.md 只留 gotchas；指令只放在工具描述里一次」。
写法要求：**必须区分两类提示词**——
- 一次性用户提示词：配料、示例、格式约束仍然有用；
- 常驻上下文（system prompt / CLAUDE.md / Skill）：要减，不要堆。
官方否定的"给示例"仅针对**工具使用**（改为设计接口），不得写成"少样本示例没用了"。

**C. 验证**：原书「git 撤销 + 人工读 diff」→ 现在「给 agent 一个能跑出 pass/fail 的检查，让它自证；独立评估器复核；人退到需求定框与结果验收两端」。

## 4. 新事实速查表（写作时只准用这里的数字）

> 完整版见 `facts/current.yaml`。下表是写正文时可直接引用的最小集。

**型号与定位**
- 顶配：Claude Fable 5.2（同底座的受限版叫 Mythos 5.2，仅限通过验证的组织）
- 日常主力：Claude Opus 5.5（官方推荐起步）
- 均衡：Claude Sonnet 5.5
- 快而省：Claude Haiku 5.5
- 官方建议：多数编码与知识工作从 **Opus 5.5 + medium effort** 起步；范围清晰的日常活降到 Sonnet 5.5；分类/路由/抽取与子任务用 Haiku 5.5；Opus 5.5 在 high 以上仍不够时才上 Fable 5.2

**价格（USD / 百万 token，输入 / 输出）**
- Fable 5.2：8 / 40（缓存读 0.20；fast mode 16 / 80）
- Opus 5.5：4 / 20
- Sonnet 5.5：2 / 10（缓存读 0.10）
- Haiku 5.5：0.10 / 0.50 起（提示超 100K 时 0.50 / 2.50）

**规格**
- 全系 1,000,000 token 上下文、128K 最大输出、知识截止 2026-06
- 自适应思考 + effort 五档：low / medium / high / xhigh / max
- 固定 `thinking: enabled/disabled` 已被拒；`tool_choice: any/tool` 改 `auto` + 严格工具使用；`computer_20251124` → `computer_toolset_20260801`

**API**
- 版本 2026-10-21 起移除 `temperature` / `top_p` / `top_k`，传了返回 400，**无替代设置**
- assistant 消息里的 document 块、user 消息里的非空 citations 也返回 400
- 缓存：每请求最多 4 个断点，5 分钟 TTL 或 1 小时 TTL（写入 2x），前缀须逐字节一致

**产品与界面**
- 统一 Claude：chat 与 Cowork 合成一个界面，对话需要代码/文件时自动转云执行；Enterprise 2026-10-23 GA
- Claude Duet：主动式 agent，跑 Opus 5.5，6000+ 连接器，研究预览；发消息/付款/签署/删除前必须人工批准，证券交易与账户转账硬禁止
- Claude Docs / Slides：可创建、编辑、导出 PDF / PowerPoint
- Claude Security：持续仓库扫描、跨仓库发现、修复跟踪（公开测试）

**Claude Code**
- Auto Mode 自 2026-08 起默认开启；关注点从"该不该批准"变成"agent 够得着什么"
- 斜杠命令并入 Skills：`.claude/commands/x.md` 与 `.claude/skills/x/SKILL.md` 等价
- 无 `CLAUDE.md` 时读 `AGENTS.md`（v2.1.277 起）
- `CLAUDE.md` 目标 <200 行，只写 gotchas；`/doctor prompt-audit` 查过时与冲突指令
- 原生 `--worktree`；`/goal` 定义完成条件；Stop hook 作确定性闸门；verification subagent 提供第二意见
- mods：TypeScript 进程内扩展，**无沙箱**，只装可信来源并锁版本

**智能体工程**
- Managed Agents 三接口：session（append-only 日志）/ harness（循环）/ sandbox（执行环境）
- 凭证不进运行生成代码的 sandbox
- Planner → Generator ⇄ Evaluator，独立评估器防自评偏见
- 上下文五杠杆：缓存稳定前缀 / 清理工具结果 / compaction / 按需检索 / 子智能体隔离

**口径冲突（正文按此写法）**
- Opus 5.5 发布：写「2026 年 9 月下旬」
- Auto Mode 默认：写「2026 年 8 月起」
- Fable 5.1 发布：写「2026 年 9 月初」
- 不写 Fable 5 出口管制暂停（仅二手）
- 只写当前 Sonnet 5.5 价格，不写 Sonnet 5 历史定价

## 5. 每章必须做的收尾

1. 章末 `## 本章要点` 重写：至少 2 条反映新现状（默认档、effort、上下文、验证任一），其余保留原判断。
2. 文件最后一行加机器可读标记（单独一行，前后空行）：
   ```
   <!-- as_of: 2026-11-14 | baseline: 2026-06-16 | refs: facts/current.yaml -->
   ```
   该行不参与渲染，供后续小批量更新定位。
3. 自检：
   - 全文搜 `4.6`、`4.8`、`4.5`、`二十万 token`、`temperature`、`extended thinking`，确认无残留旧事实（除非在讲历史沿革）。
   - 四类提示框标签与数量不比原章少。
   - `## 本章要点` 存在且有 5 条以上。
   - 无禁止词（见 §2.4）。
   - UTF-8 + LF 行尾。

---

## 6. 后续小批量更新怎么走

1. 只改 `facts/current.yaml` 与受影响段落，不动整章。
2. 每章末尾的 `as_of` 标记更新为新核对日期。
3. 在 `CHANGELOG.md` 追加一条：日期 / 章节 / 事实 id / 一句话说明。
4. 不改章节号、不改标题、不重排结构。
