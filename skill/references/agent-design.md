# 智能体与自动化

## 1. 智能体闸门

| 判据 | 结论 |
|---|---|
| 步骤能由构建者预先写死、模型只填零件 | `workflow` |
| 每步依赖上一步结果、步骤无法预先规划、模型自定下一步 | `agent` |
| 用户只说「想自动化」但未给出不确定性证据 | `workflow`，并写入 `rejected` |

- 闸门未通过时不得输出 `agent`，不得建议 Agent SDK / 子智能体 / 编排者。
- 看着需要智能体的问题多数需要工作流。

## 2. 六种模式 + 验证回路

| 模式 | 定义 | 适用 |
|---|---|---|
| `single_call` | 一进一出，一次调用产出答案 | 分类、总结、字段抽取；能成就判其它模式为过度设计 |
| `chain` | 固定调用串，前一步输出喂下一步 | 一次调用干太多开始毛糙；接缝处需查看校验 |
| `router` | 一次调用只做分类分派 | 混合负载分诊，便宜档分诊、贵档处理 |
| `orchestrator_worker` | 协调者动态拆子任务派给执行者并综合 | 任务含彼此独立、分开专注更划算的块 |
| `evaluator_optimizer` | 产出—挑刺—修订循环，直到过线 | 质量优先、且「够好」能被清楚定义 |
| `human_in_loop` | 织进其它模式的审批卡口 | 花钱、外发消息、改动要紧数据、不可逆动作 |

- 任何模式都要叠一层 `verification_loop`：能跑出 pass / fail 的检查。
- 生产系统可为多模式组合；每多一层复杂度须在 `rejected` 说明为何更简单的模式不够。

## 3. 自动化三问

| 问 | 不通过的处理 |
|---|---|
| 发生频率与人力消耗是否足够上量？ | 低频任务不自动化，写入 `rejected` |
| 能否清楚写下「做对了」长什么样？ | 成功标准写不出 → 不搭系统，写入 `open_questions` |
| 一次失败要赔多少？ | 代价越高人工监督越多；灾难性且难挽回 → 留给人手 |

- 第一套自动化甜区：频繁 + 定义清楚 + 容错，如分诊、打标、起草、提取、初轮摘要。
- 不得自动化用户从没亲手做过或只做过几次的活。

## 4. 规则

| ID | 规则 | src |
|---|---|---|
| G01 | 智能体循环固定四拍：模型决定 → 工具运行 → 模型观察结果 → 循环至完成或卡住 | book:29,31 |
| G02 | 验证优先于生成：先给一条能跑出 pass / fail 的检查（测试、构建退出码、linter、截图比对），再谈自动化 | cur:cc.goal |
| G03 | 多步系统逐步骤选「模型 × effort」，不给整系统只定一个档位 | book:31,cur:model.effort |
| G04 | 瞬时故障用带退避的重试；行动前校验每一个输出；失败时备好转人或安全默认值的兜底 | book:31 |
| G05 | 工具调用是一场协商：模型请求工具与参数，调用方执行并回传结果；工具错误作为结果返回，不抛异常退出 | book:30 |
| G06 | 工具 schema 的描述质量优先于模型能力；写清用途、何时用、尤其何时别用 | book:30 |
| G07 | 互不依赖的工具调用并行执行，按 id 回收结果 | book:30 |
| G08 | 计算机操作靠截图与点击自动化无 API 的软件；慢、贵、易错，仅在无干净接口时使用 | book:30 |
| G09 | 视觉只添感官不添手；与工具调用组合时先读图再动作 | book:30 |
| G10 | 计算机操作与视觉启用前先确认权限范围与人工确认点 | book:30,34 |
| G11 | 成本与延迟靠缓存、路由分流、逐步骤档位、批量处理控制；跑得动但太贵会被关掉 | book:28,31 |
| G12 | 权限护栏按最小权限设定；子智能体各自独立上下文并回传摘要 | book:29 |
| G13 | 会话记忆靠窗口外的只追加事件日志持久化，比 compaction 更彻底；按位置取回，不假设跨调用自动保留 | cur:agent.managed_three |
| G14 | 步骤能写死就用工作流，别让模型自定路径 | book:31 |
| G16 | `stakes=high` 或质量可定义时，用独立评估器（干净上下文 + 明确 rubric），不让生成者给自己打分 | cur:agent.evaluator_split |
| G17 | 三种闸门强度按需选：提示里要求跑检查 / `/goal` 每轮复核 / Stop hook 确定性拦住结束 | cur:cc.goal |
| G18 | harness 每个组件登记其依赖的模型假设，模型升级后逐项复核并删除已无必要的补丁 | cur:agent.harness_decay |
| G19 | Managed Agents 把 session / harness / sandbox 拆成三个接口；容器挂了当工具调用失败重试 | cur:agent.managed_three |
| G20 | 凭证永远不进运行生成代码的 sandbox；Git 用 clone 注入 token，MCP 用 vault + proxy | cur:agent.credential_isolation |
| G21 | 多智能体常态：worktree 隔离、agent view 看会话、routines 定时、跨会话消息；先解决隔离再谈并行 | cur:cc.worktree,cur:agent.context_hygiene |

## 5. 失败模式 → 防线

| 失败模式 | 必配防线 |
|---|---|
| 绕圈 / 两状态来回摆 | 硬性迭代上限 |
| 对工具或参数产生幻觉 | 校验 + 收紧的 schema |
| 长运行跑偏丢主线 | 会话聚焦、阶段性重述目标、session log 可回退 |
| 工具超时 / 外部服务不可用 | 带退避重试 + 转人兜底 |
| 输出含错误数字或引文 | 逐项核实 + 评测集回归 + 独立评估器 |
| 不可逆动作被随意执行 | 确认卡口 + 权限收紧 + 可回滚路径 |
| 静默失败无人发现 | 上线后监控与告警 |
| 自评偏见（给自己打高分） | 独立评估器 + 明确 rubric |

## 6. 输出映射

| 条件 | `pattern` |
|---|---|
| 一次调用可完成 | `single_call` |
| 固定多步、可校验接缝 | `chain` |
| 输入需分类分派 | `router` |
| 独立子任务需动态分工 | `orchestrator_worker` |
| 质量可定义且比速度重要 | `evaluator_optimizer` |
| 含不可逆或外部副作用 | 叠加 `human_in_loop` |
| 步骤无法预先规划 | `agent` |
| 需要托管执行环境与多时区会话 | `managed_agent` |
| 有 pass / fail 检查需要每轮复核 | 叠加 `verification_loop` |
