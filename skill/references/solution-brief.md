# 方案固化（SOLUTION.md）

## 1. 适用判定

| 命中 | 不命中 |
|---|---|
| 先出方案 / 规划再做 | 直接要成品代码、文案、文档 |
| 把这个需求做成可执行的方案 | 只问某个 API 怎么用 |
| 沉淀成文档，后面让别的模型照着做 | 一次性问答 |
| 用强模型规划、弱模型执行 | — |

核心用途：**把强模型的规划质量固化成文件，让后续低一档模型按同样思路执行**。一次投入，长期复用。

## 2. 输入槽位

| 字段 | 必需 | 说明 |
|---|---|---|
| `need` | 是 | 用户原始需求，原话优先 |
| `success_criteria` | 否 | 怎么算做成；缺失时给建议并进 `open_questions` |
| `constraints` | 否 | 时间、成本、技术栈、合规、不可动的边界 |
| `executor` | 否 | 后续执行者：`same_model` / `weaker_model` / `human` |
| `artifacts` | 否 | 已知要产出的文件、目录、接口 |
| `context` | 否 | 现有代码、文档、数据的位置 |

## 3. 五步流程

1. **复述与定框**：一句话写清「要什么、怎么算成功、什么绝对不能碰」。与原意不符先确认。
2. **分析需求**：拆出隐含约束与失败模式，列出 2–3 条可选路线。
3. **做取舍**：选一条，写明为什么选它、否掉了什么、否掉的理由。**这是本文件最关键的部分**——不写取舍，弱模型会重新发明一遍。
4. **写执行计划**：步骤化，每步给「输入 → 动作 → 产物 → 验证判据」。
5. **落盘为 `SOLUTION.md`**：按 §5 结构写入项目根目录；同时输出「交给执行模型的指令块」。

- 方案写完不等于任务完成。执行由用户决定：同一个模型继续、换弱模型、或交给人。
- 换模型执行时，先按 §6 做一次能力折算。

## 4. 写作要求

| ID | 规则 |
|---|---|
| B01 | 必须写「否决项」：至少一条被否掉的路线 + 否决理由。只写结论不写取舍的方案判为不合格 |
| B02 | 每一步必须有可验证的产物或判据；写不出判据的步骤要标 `open_questions` |
| B03 | 不得虚构 API、参数、配额、库版本；不确定写「待核实」并给核实方法 |
| B04 | 方案必须自包含：把执行所需的背景、约束、命名约定写进文件，不依赖对话上下文 |
| B05 | 面向弱模型执行时，指令要更显式：给字段、给示例、给边界；面向同模型可留判断空间 |
| B06 | 不得把「优化提示词」当成本能力的替代：前者改一条 prompt，后者产出可复用的执行蓝图 |

## 6. 换模型执行时的能力折算

强模型规划、弱模型执行时，按以下规则补偿，否则质量会掉：

| 项 | 处理 |
|---|---|
| effort | 执行模型至少用 `medium`；步骤多或涉及判断时用 `high` |
| 上下文 | 把 §1–§4 整段放入；不要把 `SOLUTION.md` 拆开只给第 4 节 |
| 指令显式度 | 弱模型需要字段、枚举、示例；把「酌情」「适当」这类词替换成具体判据 |
| 自检 | 每步执行完要求回报「产物 + 判据结果」，不通过就停，不许往下滚 |
| 评估 | 完成后另起一次干净调用来验收，不让执行者给自己打分 |
| 范围 | 一次只让它做 §4 里的一到两步，不要整份丢过去 |

## 7. 输出 schema

```yaml
solution_card:
  task: "<任务名>"
  path: "SOLUTION.md"
  intent: "<一句话复述>"
  chosen: "<选定路线>"
  rejected:
    - option: "<被否路线>"
      reason: "<为什么否>"
  steps: <步骤数>
  executor: same_model | weaker_model | human
  executor_config:
    model: opus | sonnet | haiku | fable | unknown
    effort: low | medium | high | xhigh | max | unknown
  verification: ["<可执行判据>"]
  risks: ["<风险 + 回退>"]
  handoff_prompt: |
    <第 7 节的可复制指令块>
  open_questions: []
  facts_used: []
```

字段约束：
- `rejected` 不得为空；为空说明没做取舍，退回重写。
- `steps` 与 `SOLUTION.md` §4 的行数一致。
- `handoff_prompt` 必须自包含，不得出现「如上」「见前文」。
- `executor=weaker_model` 时 `executor_config.effort` 不得低于 `medium`。

## 8. 反模式

- 只写步骤不写取舍——弱模型会把否决过的路线又走一遍。
- 把方案写成一堆「建议」「可以考虑」——执行者无法判断优先级。
- 方案依赖对话上下文——换个会话就失效。
- 一次把整份方案丢给弱模型——应逐步执行、逐步验收。
- 方案里写死易变的型号与价格——从事实台账取，或写「以官方文档为准」。
